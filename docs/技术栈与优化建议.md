# 技术栈与优化建议（2026-03）

本文面向维护者，聚焦三件事：**技术栈现状**、**版本策略**、**性能优化路径**。

## 1. 技术栈现状

### 1.1 核心框架

- 语言：TypeScript（严格模式）
- UI：Svelte 5
- 构建：esbuild
- 样式：Sass
- 测试：Jest + ts-jest + esbuild-jest
- 质量：ESLint + svelte-check
- 函数式工具：fp-ts
- 状态管理：Svelte stores

### 1.2 与 Obsidian 的关键耦合

- Obsidian API（`obsidian`）
- Dataview 插件 API（可选依赖）
- 插件产物固定三件套：`main.js`、`manifest.json`、`styles.css`

## 2. 版本与依赖策略

## 2.1 当前观察

- CI 使用 Node.js 18.x（`.github/workflows/*.yml`）
- 依赖检查执行 `npm outdated`，当前未返回可升级列表（可能已接近 lockfile 版本上限）

## 2.2 建议策略

### A. 运行时稳定优先

- Obsidian 插件场景建议继续以“保守升级”为主。
- 避免同时升级太多基础依赖（Svelte、esbuild、TypeScript、eslint）导致排障困难。

### B. Node 版本策略

- CI 维持 Node 18.x 可保证兼容性。
- 可新增一个非阻塞 matrix（Node 20）用于前瞻验证，不影响主线发布。

### C. 升级节奏

建议按“批次”升级并每批都跑全量检查：

1. 工具链批次：TypeScript / ESLint / Prettier
2. 构建批次：esbuild / svelte-preprocess
3. UI 批次：Svelte 生态依赖
4. 业务批次：dataview / uuid / dayjs 等

## 3. 性能优化建议

## 3.1 高优先级（建议优先做）

### 1) DataFrameProvider 查询节流/去抖

现状：项目切换、数据源变更时会触发 `queryAll()`。

建议：

- 对短时间内重复触发进行去抖（例如 100~300ms）。
- 为同一项目配置建立“查询中状态”与“最后一次结果缓存”，避免重复全量拉取。

### 2) 文件事件增量更新进一步细化

现状：frontmatter 数据源已支持增量合并，但 Dataview 路径会触发重查。

建议：

- 对 Dataview 项目增加可选“低频刷新模式”（例如定时或用户手动刷新）。
- 高频文件变更时合并事件（batch）后再刷新，减少频繁 query。

### 3) 大项目保护阈值

现状：已有 `projectSizeLimit`。

建议：

- 在 UI 明确提示“当前数量/阈值”，并提供快速调整入口。
- 记录被限制时的统计信息（例如多少文件被截断）以便排查。

## 3.2 中优先级（可逐步推进）

### 4) frontmatter 编解码热点优化

- 批量更新字段时减少重复解析。
- 合并同一文件的多次写入（写队列/写合并）。

### 5) 视图层渲染优化

- 表格与看板在大数据量时增加虚拟滚动（或分页）。
- 对昂贵计算（排序、过滤）做缓存。

### 6) 观测性建设

- 增加调试日志开关（默认关闭）。
- 记录关键路径耗时：queryAll、merge、updateRecord。

## 4. 风险点与注意事项

1. Dataview API 变化会直接影响 dataview 数据源。
2. 设置 schema 升级要有迁移函数，避免用户配置损坏。
3. 字段类型推断变化要谨慎，避免历史数据渲染错乱。
4. 移动端性能与桌面端差异较大，优化需在两端都验证。

## 5. 推荐执行顺序（两周版本）

- 第 1 周：可观测性 + 查询去抖 + 文档补齐
- 第 2 周：批量更新写合并 + Dataview 低频刷新策略 + 回归测试
