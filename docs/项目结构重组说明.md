# 项目结构重组说明（第一阶段）

本次重组目标：在**不破坏功能**的前提下，先把“根目录杂糅”的配置与脚本进行职责拆分。

> 2026-03 第二阶段已启动：引入 `src/core` 承接插件核心入口，并保留旧入口文件作为兼容转发层。

## 1. 重组后的顶层结构

- `src/`：业务源码（插件逻辑、UI、数据层）
  - `src/core/`：插件核心编排层（入口、事件、视图桥接）
- `config/`：工程配置
  - `config/build/esbuild.config.mjs`
  - `config/lint/eslint.config.mjs`
  - `config/test/jest.config.cjs`
- `scripts/`：可执行脚本
  - `scripts/release/version-bump.mjs`
  - `scripts/release/version-beta-manifest.mjs`
- `docs/`：维护文档与工程指南

## 2. 本次实际迁移项

### 2.1 配置文件迁移

- `esbuild.config.mjs` → `config/build/esbuild.config.mjs`
- `eslint.config.mjs` → `config/lint/eslint.config.mjs`
- `jest.config.js` → `config/test/jest.config.cjs`

### 2.2 发布脚本迁移

- `version-bump.mjs` → `scripts/release/version-bump.mjs`
- `version-beta-manifest.mjs` → `scripts/release/version-beta-manifest.mjs`

### 2.3 引用同步

- `package.json` scripts 已全部切换新路径
- `.github/workflows/ci.yml` 已切换新版 beta manifest 脚本路径
- `docs/维护指南.md` 已同步更新脚本路径

## 3. 重组原则（本次遵守）

1. **先分层、后深改**：先解决结构可读性，再推进业务代码迁移。
2. **保证兼容**：重组后 `build/test/lint/svelte-check` 必须可跑。
3. **低风险迭代**：避免一次性移动大量业务源码导致回归难以定位。

## 4. 下一阶段建议（可选）

如果你愿意继续，我建议按下面顺序做“第二阶段重组”：

1. `src/` 内按职责再拆：`core/`、`features/`、`shared/`
2. 为 `ui/views/*` 建立统一约定（组件、hooks、types 同构）
3. 增加 `tests/fixtures` 与测试工具目录，统一测试组织方式
4. 建立 `CONTRIBUTING` 内的目录与命名规范章节

---

本次重组是“工程骨架优化”，不是业务逻辑重写；优点是见效快、风险低，适合作为长期维护的起点。
